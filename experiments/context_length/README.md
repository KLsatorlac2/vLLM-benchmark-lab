# Context Length

扫描 `max_model_len=4096/8192/16384`，同时记录真实输入 token 长度。不要把配置上限直接当成实际上下文长度，比较显存、吞吐和尾延迟。

## 本轮结果（2026-09-26，Qwen2.5-0.5B，RTX 4060）

**设计**：前四组的**总 prefill token 固定为 8192**，只改单条长度与 batch 宽度，
这样延迟变化只来自"单条变长"，而不是"总工作量变多"。
`max_tokens=64`，`gpu_memory_utilization=0.75`。

| 单条长度 | batch 宽度 | 总 prefill | batch 延迟 | batch 吞吐 | `max_model_len` |
| --- | --- | --- | --- | --- | --- |
| 512 | 16 | 8192 | 1373.90 ms | 745.32 tok/s | 1024 |
| 2048 | 4 | 8192 | 1404.20 ms | 182.31 tok/s | 2560 |
| 4096 | 2 | 8192 | 1545.25 ms | 82.83 tok/s | 4608 |
| 8192 | 1 | 8192 | 1475.21 ms | 43.38 tok/s | 8704 |
| **16384** | 1 | **16384** | 2212.62 ms | 28.92 tok/s | 16896 |

实际 `input_tokens` 与"单条长度"逐条核对一致，**不是配置上限**。

### 两条结论

1. **总工作量不变时，延迟与单条长度基本无关**：前四行落在 1374–1545 ms（×1.125），
   且**不单调**（4096 那组反而比 8192 高）。**prefill 代价正比于总 token 数，不是单条长度。**
2. **吞吐的暴跌是 batch 宽度效应，不是长上下文效应。** 前四行总 prefill 相同、延迟几乎相同，
   变的只有 batch 宽度（16→1）和输出总量（1024→64 token）。
   **这张表不能读成"上下文越长吞吐越低"。**

**16384 vs 8192**（同为 batch 宽度 1，工作量翻倍）：1475.21 → 2212.62 ms，**×1.50**。
2 倍 token 换 1.5 倍时间，慢于线性但同量级。

0.5B 的 KV cache 约 12 KB/token，16384 只需约 196 MB，**8GB 上没有任何显存压力**。
本轮**没有采集伴随的 GPU 遥测**，所以上表没有显存列。

分析见 `docs/benchmark_report.md` 第 7 节。
