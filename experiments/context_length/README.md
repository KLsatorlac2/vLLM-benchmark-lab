# Context Length

扫描 `max_model_len=4096/8192/16384`，同时记录真实输入 token 长度。不要把配置上限直接当成实际上下文长度，比较显存、吞吐和尾延迟。

## 本轮结果（2026-09-26，Qwen2.5-0.5B，RTX 4060）

**设计**：前四组的**总 prefill token 固定为 8192**，只改单条长度与 batch 宽度，
这样延迟变化只来自"单条变长"，而不是"总工作量变多"。
`max_tokens=64`，`gpu_memory_utilization=0.75`。

| 单条长度 | batch 宽度 | 总 prefill | batch 延迟 | batch 吞吐 | `max_model_len` |
| --- | --- | --- | --- | --- | --- |
| 512 | 16 | 8192 | 1373.90 ms | 745.32 tok/s | 1024 |
| 2048 | 4 | 8192 | 1404.20 ms | 182.31 tok/s | 2560 |
| 4096 | 2 | 8192 | 1545.25 ms | 82.83 tok/s | 4608 |
| 8192 | 1 | 8192 | 1475.21 ms | 43.38 tok/s | 8704 |
| **16384** | 1 | **16384** | 2212.62 ms | 28.92 tok/s | 16896 |

实际 `input_tokens` 与"单条长度"逐条核对一致，**不是配置上限**。

### 两条结论

1. **总工作量不变时，延迟与单条长度基本无关**：前四行落在 1374–1545 ms（×1.125），
   且**不单调**（4096 那组反而比 8192 高）。**prefill 代价正比于总 token 数，不是单条长度。**
2. **吞吐的暴跌是 batch 宽度效应，不是长上下文效应。** 前四行总 prefill 相同、延迟几乎相同，
   变的只有 batch 宽度（16→1）和输出总量（1024→64 token）。
   **这张表不能读成"上下文越长吞吐越低"。**

**16384 vs 8192**（同为 batch 宽度 1，工作量翻倍）：1475.21 → 2212.62 ms，**×1.50**。
2 倍 token 换 1.5 倍时间，慢于线性但同量级。

0.5B 的 KV cache 约 12 KB/token，16384 只需约 196 MB，**8GB 上没有任何显存压力**。
本轮**没有采集伴随的 GPU 遥测**，所以上表没有显存列。

分析见 `docs/benchmark_report.md` 第 7 节。

## Kaggle T4 ×2 / Qwen2.5-1.5B（2026-09-27）

同一设计：**总 prefill token 固定为 8192**，只改单条长度与 batch 宽度。
`max_tokens=64`、`gpu_memory_utilization=0.85`、`dtype=half`、**引擎 V0**。

| 单条长度 | batch 宽度 | 总 prefill | batch 延迟 | batch 吞吐 | 语义 |
| --- | --- | --- | --- | --- | --- |
| 512 | 16 | 8192 | 2364.44 ms | 433.08 tok/s | batch |
| 2048 | 4 | 8192 | 2346.75 ms | 109.09 tok/s | batch |
| 4096 | 2 | 8192 | 2373.16 ms | 53.94 tok/s | batch |
| 8192 | 1 | 8192 | 2748.77 ms | 23.28 tok/s | **single** |
| **16384** | 1 | **16384** | **5760.25 ms** | **11.11 tok/s** | **single** |

实际 `input_tokens` 与"单条长度"逐条核对一致，**不是配置上限**。

### 结论一：本机那条核心发现被独立复现 ✅

只看 batch 宽度 ≥2 的三行（总 prefill 都是 8192）：
**2346.75 – 2373.16 ms，极差仅 1.13%**。

本机在同一设计下的极差是 **1.125%**。

> **两台机器、两个模型、两个引擎、两种 dtype，得到同一个 1.1% 量级的极差。**
> 这是整个项目里**最可复现的一条结论**：
> **总 prefill 量不变时，延迟与单条序列长度基本无关**，
> prefill 代价正比于**总 token 数**而非单条长度。

### 结论二：吞吐暴跌依旧是 batch 宽度效应

吞吐 433.08 → 23.28（×0.054）看起来像"长上下文很慢"，但前四行总 prefill 相同、
延迟几乎相同，变的只有 batch 宽度 16→1 与输出总量 1024→64。
**这张表不能读成"上下文越长吞吐越低"。**

### 结论三：16384 的代价在 T4 上是线性的，本机是次线性的

8192 → 16384（batch 宽度同为 1，工作量翻倍）：

| | 8192 | 16384 | 倍数 |
| --- | --- | --- | --- |
| 本机 4060 / 0.5B / bf16 / FlashAttention | 1475.21 ms | 2212.62 ms | **×1.50** |
| T4 / 1.5B / fp16 / XFormers | 2748.77 ms | 5760.25 ms | **×2.10** |

**候选解释（无法分离，均为假设）**：attention backend 差异最贴合"倍数随长度增长"这个现象
（本机 FlashAttention、T4 XFormers），但**模型规模与硬件也同时变了**，本次无法区分。
**attention backend 没有被记进产物**，这是报告 Part II 第 23.2 节 #3 那条局限。

### 一致性交叉检查

`context-512`（16×512，`max_num_seqs=16`）= 2364.44 ms；
`concurrency-16`（64×512，`max_num_seqs=16`）= 9263.90 ms。

64 请求在 `max_num_seqs=16` 下正好是 4 个调度轮次：4 × 2364.44 = 9457.76 ms（若严格线性），
实测 9263.90 ms（**好 2.05%**）。**两个不同 prompt 文件、不同实验批次的 run，
在同一个批次形态上吻合到 2%**——离线 runner 的批计时口径是稳定的。

分析见 `docs/benchmark_report.md` Part II 第 17 节。
